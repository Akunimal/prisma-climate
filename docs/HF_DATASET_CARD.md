# PRISMA daily forecast archive

Daily archived ensemble forecasts for the 19 configured stations in Argentina,
produced by [PRISMA](https://github.com/Akunimal/prisma-climate), an open
forecast-verification project. Past ensemble forecasts are only partially
re-fetchable from the provider: member values for past valid times are retained
for about 3 days, but the past run's issue-dated lead structure is not
reconstructible (probed 2026-11-13: with `past_days` the future segment is
identical to a fetch without it, i.e. the current run; past-day cells do not
match the archived issue-dated forecasts; the payload carries no run/cycle id),
so a missed day cannot be repaired into verification data, and no deep
uniform-cycle ensemble backfill exists: every issue date is archived on the day
it is retrieved, and a missed day is lost verification data.

## Layout

```
forecasts/<issue_date>/openmeteo-ensemble_<issue_date>.parquet
observations/smn/<dato>/<date>/<dato>.zip
observations/smn/<dato>/<date>/manifest.json
```

`forecasts/` holds one file per issue date. The issue date is read from the
parquet's `issue_time` column and never from the runner clock, and an existing
path is skipped rather than overwritten, so the **first archive of an issue date
is canonical and frozen**.

`observations/smn/` holds the SMN Argentina open-data payloads exactly as
served, one ZIP plus its `manifest.json` per capture, for the three payloads
`regtemp`, `datohorario` and `observaciones`.

## Observation archive (`observations/smn/`)

Captured by a dedicated workflow, `.github/workflows/observations.yml`, which is
isolated from the forecast archive by construction: its own schedule, its own
concurrency group (`observations-archive`), `contents: read` and **no push step
at all**, so it never commits to `main` and an SMN failure fails only that
workflow. Its run status travels in the `github_run` block of the manifest it
writes here instead of in a heartbeat commit.

- **Schedule** (observed in the workflow file, `ubuntu-latest`):
  `datohorario` and `observaciones` daily at **07:17, 11:41 and 19:09 UTC**
  (three attempts, because both endpoints serve only the latest completed LOCAL
  day), and `regtemp` weekly on **Mondays at 04:34 UTC**. `workflow_dispatch` is
  enabled and runs all three payloads.
- **Date keys come from the payload, never from the runner clock.** The daily
  key is the payload's `FECHA` (DDMMYYYY, local calendar day); `regtemp` is
  keyed by the **last `FECHA` of the served window**, because the endpoint
  serves a rolling 365-day window and the retrieval instant belongs in
  `manifest.json` (`retrieved_at`), never in the path. An existing target is
  skipped, so the **first capture of a date is canonical and frozen**, and no
  observation is ever written under `forecasts/` or touches forecast keying.
- **Manifest contents:** endpoint, payload member, `retrieved_at`, capture key
  and where it came from, served window (first/last `FECHA`, distinct days), row
  count, sha256 of the ZIP as served, field list, `local_calendar` day-convention
  evidence, SMN attribution and licence, the Hugging Face target, and the
  GitHub Actions run (workflow, run id, attempt, event, cron that fired, head
  sha, run URL).
- **`regtemp` provenance:** the capture the published discrepancy results and
  the frozen climatology adjustment were computed from was retrieved locally at
  `2026-11-12T01:41:32Z` with window `2025-11-11` → `2026-11-10` (42,953 rows,
  sha256 `28b166d87e618df127cb2e7bb932e4b6c813b0ab4e489e860cc542bf5902af98`). It
  was published to `observations/smn/regtemp/2026-11-10/` through the GitHub
  Release `observations-regtemp-2026-11-10`, mirrored by
  `.github/workflows/hf-backfill.yml` in one commit: the mirror re-checks the
  pinned sha256 of the ZIP and of its text member, and the manifest is
  regenerated by `scripts/capture_observations.py` (never hand-edited) with
  `retrieval.mode: local` and `publication.channel: github_release_mirror`.
  Every later snapshot's manifest states whether its window starts later than
  that capture, so two snapshots are never presented as a day-for-day superset:
  the endpoint is a rolling window and the earlier days have rolled off.
- **No backfill:** probed 2026-11-13, the `fecha` query parameter is ignored by
  these endpoints — a request for `fecha=20261111` returned
  `datohorario20261112.txt` (`FECHA 12112026`) — so each day is captured on the
  day it is served and a missed day is lost, exactly like a missed issue date in
  `forecasts/`.

## Update frequency

Scheduled at **06:47, 09:47, 12:17, 14:43 and 18:31 UTC** (redesigned 2026-11-13 after
the delays observed on 2026-11-12: the original 06:47 slot kept for spread,
mid-day attempts weighted into 09:00-15:00 UTC; previously 06:47, 12:17 and
18:31 UTC) by
the `Daily forecast archive` workflow (`.github/workflows/ingest.yml`) on
`ubuntu-latest`. **The schedule is proven as of 2026-11-12:** the first
`event=schedule` run completed that day (run 43249798026, conclusion `success`,
headSha `1e82b23`, started 15:37 UTC — the 12:17 UTC slot, ~3h20m late), and
two more schedule runs started 19:52 and 23:44 UTC that day (runs 43294532842
and 43331372851, both `success`), hours after their nominal slots; GitHub
documents scheduled runs as best-effort and subject to delay or drop under
load. Before them, the 2026-11-12 file was archived by a manual
`workflow_dispatch` rescue, and the scheduled runs themselves were data no-ops
(the canonical file already existed). The archive path itself is proven
(skip-if-exists keeps the first file of an issue date canonical).

**Residual risk:** a schedule slot can be delayed or dropped, a UTC day with no
successful run is lost verification data, and nothing self-heals; a watchdog
records missing days in the repository's ingest status for visibility only and
never repairs them — it reads the archive through an HF listing that can be
cache-prone, so a reported missing day may be a false positive. This card is
generated by
`scripts/generate_dataset_card.py` and published by
`.github/workflows/hf-backfill.yml`.

## Schema

Every row follows the PRISMA connector contract (plan section 3.3):

| field | required | meaning |
|---|---|---|
| `variable` | yes | `t2m_max`, `t2m_min`, `precip` |
| `unit` | yes | `degC` for temperature, `mm` for precipitation |
| `lat`, `lon` | yes | station coordinates (from `ghcnd-stations.txt`, see the repository docs) |
| `time` | yes | UTC date of the forecast target, no time zone |
| `source` | yes | source id from `configs/sources.yaml` (`openmeteo-ensemble`) |
| `value` | yes | the forecast value |
| `quality_flag` | yes | `ok` / `suspect` / `fail` |
| `location` | yes | configured station name |
| `member` | no | ensemble member index: 0-30 for `gfs_seamless`, 0-50 for `ecmwf_ifs025` |
| `lead_day` | no | forecast lead in days, 0-15 |
| `model` | no | `gfs_seamless` or `ecmwf_ifs025` |
| `day_convention` | yes | `local_calendar` - the value is aggregated over the local calendar day |
| `issue_time` | no | **download-time proxy** in UTC; see the note below |
| `retrieved_at` | yes | UTC instant the provider was queried |
|

`issue_time` is a **download-time proxy**, not a model initialisation time. The
provider does not expose the model cycle time, so PRISMA records the UTC fetch
instant instead (plan section 3.3, `docs/PLAN.md`). Two files with different
`issue_time` values are two fetches, not necessarily two model cycles.

## Contents

- Models: `gfs_seamless` and `ecmwf_ifs025`, both served by the Open-Meteo
  Ensemble API.
- 19 locations, 16 forecast days (`lead_day` 0-15), 31 member indices for GFS
  and 51 for ECMWF IFS.
- Variables: `t2m_max`, `t2m_min` (degC) and `precip` (mm).

## Evaluation gate

Skill metrics and any leaderboard are published only once **15 distinct issue
dates** are archived. Counting starts at 2026-11-11, so the earliest possible
15th distinct issue date is **2026-11-25** if every day archives. The
hypothesis threshold **X = 60%** — the minimum share of stations in which local
calibration must reduce CRPS versus the raw ensemble while keeping 90% nominal
reliability — is frozen and is not re-thresholded; see `docs/EVALUATION_PROTOCOL.md`.
